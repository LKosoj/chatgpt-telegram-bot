# Оптимизация промптов, инструментов и скиллов

Цель — убрать повторные обращения к модели и сократить объём данных в запросах, сохранив шаги, необходимые для результата. Работаем в текущей копии проекта, с локальными тестами в `.venv`. Для объёмных скиллов исходным каталогом считаем обнаруженный `bot/skills`. Он исключён из Git, поэтому изменения в нём проверяются и перечисляются отдельно. Проверка работающего Telegram-бота и платные вызовы моделей в эту работу не входят.

## 1. Каталог, установка и порядок работы в skills_agent

- Сделать встроенный краткий каталог основным источником при выборе скилла. Вызывать `list_skills` при явном запросе списка или когда нужен актуальный список с диска. Для обычной работы использовать идентификатор из каталога или результат установки.
- При нескольких подходящих источниках спросить, какой выбрать. Для выбранного источника оставить подтверждение кнопками внутри `install_skill`. Если после подтверждённого обращения к источнику инструмент обнаружил несколько скиллов, сначала нужен выбор, затем подтверждение нового вызова с конкретным набором. Учесть прямую ссылку и `install_all`. Применить то же правило к созданию скилла, которое уже требует подтверждения внутри инструмента.
- Согласовать порядок чтения инструкций, создания плана, активации и загрузки материалов текущего этапа. Сохранить требования к презентациям, проверке результата, запросу решения у пользователя и финальной доставке. Убрать повторяющиеся формулировки в системной инструкции.
- Проверка. Известный скилл можно выбрать без списка. Установка из известного источника требует одного подтверждения. Сложная работа содержит план перед первым действием, которому он нужен. Для материалов с независимыми чтениями сохраняется параллельное выполнение.

## 2. Однократная загрузка SKILL.md

- Оставить текущий ответ `get_skill` и совместимость существующих вызовов `activate_skill`.
- После предварительного чтения скилла дать модели возможность вызвать существующий `activate_skill` без повторной передачи полного текста. Проверить минимальный способ в схеме и реализации плагина. Если инструкция ещё не читалась, обычная активация должна вернуть её.
- Проверка. Оба пути дают доступ к одному экземпляру текста инструкции. Активация сохраняет текущее состояние и доступ к дополнительным файлам и скриптам. Старые вызовы без дополнительного параметра работают как прежде.

## 3. Меньше описаний инструментов в запросах

- Проследить основной цикл и повторные запросы. Если выполнение инструментов уже закрыто через `tool_choice=none`, исключить их описания из фактического запроса и расчёта его объёма.
- Сохранить режимы, где доступен полный набор, и текущие ограничения пользователя. Проверить сценарии, в которых нужен отдельный инструмент доставки или создания плана. Оставить эти инструменты доступными на соответствующих шагах.
- Для редактора текста оставить поиск и чтение источников (`web_research`, `ddg_web_search`, `website_content`), работу с документом (`text_document_qa`) и явную оптимизацию промпта (`prompt_perfect`). Озвучка, транскрипция YouTube и напоминания остаются доступны в общем режиме.
- Проверка. Финальный запрос без доступных инструментов не включает их описаний. В промежуточном запросе доступен нужный инструмент, итоговая доставка и обработка истории сохраняются.

## 4. Prompt Perfect

- В общем режиме `assistant` убрать автоматический вызов из правила о кратких или нечётких запросах. Ясную просьбу выполнять сразу, существенную неясность уточнять. Если пользователь попросил только улучшить промпт, вернуть ему переписанный текст. Инструкции по автоулучшению в остальных режимах сохраняются.
- Проверить связанный текст режима и документацию, описывающую это правило.
- Проверка. Короткий вопрос можно обработать без вспомогательной модели. Явная оптимизация промпта по-прежнему доступна.
- Новая инструкция применяется при выборе режима. Если в существующей сессии сохранён прежний текст, повторный выбор того же режима обновляет его и сохраняет историю.

## 5. Большие инструкции скиллов

- Для `powerpoint` и `research-paper-writing` оставить короткие входные инструкции с правилами, общими для всех этапов. Вынести длинные справочные части в материалы по этапам с рабочими относительными ссылками. Сохранить условия запуска скриптов, выбор материалов и проверки результата.
- Использовать существующий способ чтения дополнительных файлов. Измерить размер входных инструкций до и после и проверить, что плагин находит перенесённые файлы, включая ссылки на связанные материалы.
- Проверка. Пользовательский запрос направляется к правильному этапу, обязательные шаги доступны из входной инструкции, ссылки разрешаются из установленного каталога.

Локальные файлы с инструкциями по этапам:

- `powerpoint/` — `workflow.md`, `creation-editing.md`, `quality.md`.
- `research-paper-writing/` — `setup-literature.md`, `experiments.md`, `drafting.md`, `review.md`, `submission.md`, `post-acceptance.md`, `paper-types.md`, `integration-reference.md`.

## 6. Порядок выполнения и приёмка

1. GPT‑6.1‑Terra составляет детальные планы для четырёх независимых областей. Изменения промптов и списка плагинов в одном YAML делает один агент, реализацию активации, цикл вызовов и локальные инструкции ведут остальные.
2. После согласования интерфейса активации области реализуются параллельно. Каждый агент ограничен своими файлами. После реализации каждой области другой агент проверяет её diff и критерии приёмки.
3. После интеграции запустить `/goal` на общий цикл ревью. Агент GPT‑6.1‑Terra проверяет весь diff, подтверждённые ошибки и предупреждения исправляются, затем проводится новое ревью. Цикл заканчивается после прохода без замечаний. После него основной исполнитель проверяет все изменения, исправляет найденное и при новых правках повторяет ревью.
4. Прогнать целевые и общие локальные тесты, проверить относительные ссылки, `git diff --check` и итоговый состав файлов. Сверить четыре сквозных сценария на существующих локальных средствах проверки. Для величин, которые можно измерить без внешнего запроса, зафиксировать сравнение до и после.

Основные риски при приёмке — потеря нужного инструмента в финальном шаге, повторное подтверждение, активация до плана, потеря обязательных условий при переносе больших инструкций и смешение правок в общем YAML. Они проверяются отдельно перед общим ревью. Срок зависит от результатов ревью и числа исправлений.
